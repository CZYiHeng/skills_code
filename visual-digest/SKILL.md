# Visual-Digest — 输出速览

其他 skill 负责"想清楚"，本 skill 负责"让用户一眼看懂"。

核心规则：**只提炼，不重新生成内容。** 速览里的每一句话都必须能在原始输出中找到出处。

## 何时使用

- 其他 skill 输出了密集内容（骨架代码、方案评审、分析报告），用户需要快速了解
- 用户说"给我图文的" / "总结一下" / "速览" / "可视化"
- 多轮任务进行中，用户想看当前进度
- 输出超过一屏，用户懒得滚动读

## 何时不用

- 原始输出本身就很短（几行结论）——直接复述即可，不要为可视化而可视化
- 用户明确要求看完整原文/完整代码
- 内容还在演进中，提炼会丢失关键上下文

## 工作流程

### 步骤 1：识别输入

确认要提炼的原始输出是什么：

| 来源 | 典型内容 |
|---|---|
| `$req-to-code` | 骨架代码、方案评审、进度摘要、TODO 清单 |
| `$solution-review` | 方案三维度、对比表、胜出论证 |
| `$flow-tracer` | 数据流、影响分析、7 规则校验结果 |
| `$code-formatter` | 函数头注入前后的差异 |
| 任意文档/报告 | 长篇分析、调研结果 |

### 步骤 2：提炼要点

从原始输出中抽取"用户决策需要的最小信息集"：

- **结论是什么**（一句话）
- **关键决策点**（需要用户做什么判断）
- **结构/流程**（东西是怎么组织的）
- **风险/缺点**（哪里弱）
- **下一步**（接下来做什么）

不要面面俱到——速览的目的是快，漏掉的细节用户会去翻原文。

### 步骤 3：选择形式

根据内容类型自动选择，不打断用户：

| 内容特征 | 形式 | 理由 |
|---|---|---|
| 有数据流 / 调用链 / DAG | **流程图** | 线性或图状结构画图比文字直观 10 倍 |
| 有方案对比 / 多选项 | **对比表 + 速览卡** | 统一维度的表是评审的最快方式 |
| 有多轮进度 / TODO 状态 | **进度仪表盘** | ✅/🔲 状态一眼看清完成度 |
| 内容超过两屏 / 需要存档 | **HTML 报告页** | 可滚动、可保存、可分享 |
| 只有一个核心结论 | **速览卡** | 一屏说清，不用别的 |
| 多种形式都适用 | **速览卡 + 一张主图** | 默认组合：先给全局，再给关键结构 |

### 步骤 4：渲染

按形式规范渲染（见下节）。

### 步骤 5：附上原文指引

速览末尾必须告诉用户原文在哪：

```
── 原文 ──────────────────
完整输出：req-to-code Round 2（上方对话）
文件：G:\project\main.py
要改哪里 / 看细节 → 翻原文；说"继续"按原计划推进
```

## 五种形式规范

### ① 速览卡

一屏能看完的摘要卡，结构固定：

```
╔══════════════════════════════════════╗
║ <主题>                     <来源 skill> ║
╠══════════════════════════════════════╣
║ 结论：<一句话>                         ║
║                                      ║
║ 要点：                                ║
║  1. <要点>                            ║
║  2. <要点>                            ║
║  3. <要点>                            ║
║                                      ║
║ ⚠ 注意：<最大的风险或缺点>              ║
║ → 下一步：<一个明确动作>               ║
╚══════════════════════════════════════╝
```

规则：结论一句话；要点 ≤5 条，每条 ≤20 字；只写最大的一个风险。

### ② 流程图 / 架构图

用于数据流、调用链、DEPENDS_ON DAG：

- 节点 = 函数/模块，标注一句话职责（不是函数名堆砌）
- 边 = 数据流向，箭头方向清晰
- 已填充/占位符用不同视觉状态区分（如实心 vs 虚线）
- 图里节点 ≤10 个——超过就分层（先画总图，细节图按需）

### ③ 对比表

用于方案评审，直接沿用 `$solution-review` 的统一维度：

| 维度 | 方案 A | 方案 B |
|---|---|---|

- 胜出的方案视觉上突出（标记 ★ 或"推荐"）
- 表后必须跟一句"什么情况下选别的"——没有适用边界的对比不完整

### ④ 进度仪表盘

用于多轮任务（如 `$req-to-code` 的 Round 状态）：

```
进度 ▓▓▓▓▓▓░░░░ 60%

主旨：<一句话主旨>

✅ read_file      — 读取 CSV 为 DataFrame
✅ clean_data     — 去重去空标准化
✅ validate_rows  — 校验必填字段
🔲 transform      — 字段映射（本轮进行中）
🔲 write_output
🔲 main

本轮变更：transform 开始填充
下一步：说"继续"填充 write_output
```

### ⑤ HTML 报告页

用于长篇输出或需要存档的内容：

- 单文件 HTML，内联样式，无外部依赖
- 结构：标题 → 速览卡（页面顶部，一屏结论）→ 分节详情 → 原文附录
- 适配当前 IDE 主题（浅色主题用浅色背景深色文字）
- 输出为文件，可直接打开/分享

## 规则

- **只提炼不重新生成**——速览内容必须能在原始输出中找到出处，禁止编造或扩写。
- **一屏原则**——速览卡、仪表盘必须一屏看完；看不完说明提炼不够狠。
- **自动选形式**——根据内容特征选择，不打断用户问"你想要哪种"；选错用户会说。
- **原文可追溯**——每个速览末尾附上原文位置（对话轮次/文件路径）。
- **不丢关键信息**——风险、缺点、待决策项必须出现在速览里；可以省略实现细节，不能省略判断依据。
- **视觉状态要诚实**——占位符就是占位符（虚线/🔲），不要把未完成的东西画成已完成。
- **适配主题**——浅色 IDE 主题下用浅色背景深色文字；深色主题反之。
- **简单内容不套形式**——几行能说清的不要画图表，直接复述。
- **中文输出**——除非用户用英文交流。

## 与其他 skill 的配合

| 场景 | 配合方式 |
|---|---|
| `$req-to-code` 每轮输出后 | 骨架 → 流程图 + 进度仪表盘；方案评审 → 对比表 |
| `$solution-review` 评审后 | 三维度 → 速览卡 + 对比表 |
| `$flow-tracer` 分析后 | 数据流 → 流程图；7 规则校验 → 仪表盘 |
| `$code-formatter` 注入后 | 前后差异 → 速览卡（改了哪些函数、各加了什么头） |
| 长篇调研/分析 | HTML 报告页 |
