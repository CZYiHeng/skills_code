# Solution-Review — 方案三问

任何技术方案在被提出时，都必须回答三个问题。方案不只是"怎么做"，还要说清"为什么这么做"以及"为什么比别的方案好"。

核心规则：**没有对比的方案没有说服力，没有动机的方案无法评审。**

## 何时使用

- AI 即将给出或已经给出技术方案，需要向开发人员解释
- 需要在多个方案之间做选择
- 用户问"为什么这么做" / "有没有别的方案" / "这个方案好在哪"
- 架构决策、技术选型、函数分解、重构方案的技术评审

## 何时不用

- 纯粹的编码实现，没有方案选择空间
- 用户明确要求只要结论不要解释

---

## 三个维度

### ① 方案是什么 — 让开发人员看懂

用开发人员能理解的语言说清方案本身。不要堆术语，要说清"它到底是怎么运作的"。

| 要素 | 要说明什么 |
|---|---|
| 一句话概述 | 这个方案做了什么 |
| 核心思路 | 关键机制/原理——用一句大白话讲明白 |
| 结构 | 涉及的模块、函数、数据结构、外部依赖 |
| 流程 | 执行步骤 |
| 代码骨架 | 关键实现（如果适用） |

**写法要求**：核心思路必须能"讲给同事听"——如果一句话讲不明白，说明方案还没想清楚。

**示例**：

```
一句话：用连接池管理数据库连接，复用而非每次新建

核心思路：启动时预先建好一批连接放在池子里，请求来了从池里取，
用完还回去而不是关闭，省掉反复创建销毁的开销。

结构：
  - ConnectionPool       — 持有连接集合，管理生命周期
  - get_connection()     — 从池取空闲连接，池空则新建（未达上限）
  - release_connection() — 用完归还，不关闭

流程：
  1. 请求到达 → get_connection()
  2. 池中有空闲 → 直接返回
  3. 池空且未达上限 → 创建新连接返回
  4. 池空且已达上限 → 等待超时或抛异常
  5. 使用完毕 → release_connection() 归还

代码骨架：
  class ConnectionPool:
      def get_connection(self) -> Connection: ...
      def release_connection(self, conn) -> None: ...
```

### ② 为什么给出这个方案 — 动机和约束

说明触发这个方案的原因。方案不是凭空来的，是约束条件下的产物。

| 要素 | 要说明什么 |
|---|---|
| 要解决的问题 | 这个方案针对什么痛点 |
| 关键约束 | 什么条件限制了我们（性能？数据量？团队能力？时间？兼容性？） |
| 触发原因 | 为什么是现在需要这个方案 |
| 不这么做的后果 | 如果不用这个方案会怎样 |

**写法要求**：约束要具体。"性能好"不够，要说"QPS 从 200 提升到 1000"；"成本低"不够，要说"1 人天 vs 3 人天"。

**示例**：

```
要解决的问题：每次请求都新建数据库连接，QPS 上去后连接创建开销成为瓶颈

关键约束：
  - 数据库最大连接数 100，不能无限创建
  - 团队熟悉连接池模式，学习成本低
  - 本周必须上线，不能引入需要学习周期的重型框架

触发原因：压测发现 QPS 200 时，连接创建耗时占请求总耗时 40%

不这么做的后果：继续每次新建连接，QPS 无法突破 300，撑不住预期流量
```

### ③ 方案优点与对比 — 说服力

列出备选方案，用统一维度对比，说明当前方案为什么胜出，以及什么情况下应该选别的方案。

**必须列出至少 1 个备选方案**——没有对比就无法论证"为什么是这个方案"。

| 对比维度 | 说明 |
|---|---|
| 性能 | 吞吐量、延迟、资源占用 |
| 复杂度 | 实现难度、代码量、理解成本 |
| 可维护性 | 后续修改、调试、排查的难易 |
| 扩展性 | 未来需求变化时能否平滑支持 |
| 开发成本 | 需要多少人天 |
| 风险 | 出错概率、出错后的影响面 |

**写法要求**：
- 对比必须用**统一维度**——不能拿 A 的性能去比 B 的开发成本
- 要**诚实说明适用边界**——什么情况下当前方案不是最优解
- 如果确实只有一种合理方案，说明"为什么没有其他选择"，而不是硬凑备选

**示例**：

```
备选方案：
  A. 连接池（当前方案）
  B. 每次请求新建连接（现状）
  C. 引入 ORM 框架（SQLAlchemy）管理连接

对比：
| 维度 | A 连接池 | B 每次新建 | C ORM 框架 |
|---|---|---|---|
| 性能 | 高（复用连接） | 低（频繁创建销毁） | 中高 |
| 复杂度 | 中（需管理生命周期） | 低 | 高（引入框架） |
| 可维护性 | 中 | 高（逻辑直白） | 高（框架成熟） |
| 扩展性 | 中（可加监控/预热） | 低 | 高 |
| 开发成本 | 1 人天 | 0（已有） | 3 人天 + 学习 |
| 风险 | 中（连接泄漏需防范） | 低 | 中（框架黑盒） |

当前方案胜出原因：
  在"本周上线 + 团队熟悉"的约束下，A 用 1 人天拿到接近 C 的性能收益，
  且不引入框架黑盒，出问题时团队能自己排查。

什么情况下应该选别的：
  - 项目周期 >1 周且团队愿意投入学习 → 选 C，长期可维护性更好
  - QPS 长期低于 50 → 选 B，够用且最简单，连接池是过度设计
```

## 与其他 skill 的配合

本 skill 定义"方案怎么表达"的规范，具体领域的方案内容由对应 skill 生成：

| 场景 | 配合方式 |
|---|---|
| `$req-to-code` 输出骨架方案 | **已集成**——req-to-code 的"思考纪律 → 每个方案做方案评审"即本框架（三维度 + 批判三问） |
| `$dev-flow` Phase 2 架构设计 | 架构方案用本框架说明，让评审者看懂并判断 |
| 重构 / 技术选型 / 架构决策 | 直接调用本 skill 评审现有方案 |
| 代码评审 | 对"为什么这么实现"的疑问，用本框架反推说明 |

## 规则

- **三个维度缺一不可**——只说"怎么做"不给"为什么"和"对比"的方案是不完整的。
- **必须列出备选方案**——没有对比就无法论证当前方案的合理性；确实没有时说明原因。
- **对比要用统一维度**——不能拿 A 的性能比 B 的成本，维度必须对齐。
- **诚实说明适用边界**——要说明什么情况下当前方案不是最优解，不做一味推销。
- **用开发人员能懂的语言**——避免堆砌术语，核心思路要能用大白话讲明白。
- **约束要具体**——避免"性能好""成本低"这类模糊表述，给出可验证的数字。
- **不要为了对比而对比**——如果只有一种合理方案，说清为什么没有其他选择。
- **方案可以演进**——约束变了方案可能不再最优，记录下当前的约束假设以便后续复评。
