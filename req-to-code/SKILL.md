# Req-To-Code — 对话式渐进开发

## 输出设计

通过多轮对话渐进式地构建代码。能推断的推断，尽量少打断。每轮输出一份设计文档，用户只看设计文档——通过设计文档理解方案、审查决策、给出反馈。

设计文档包含：前提条件、主旨、方案评审（三维度：是什么/为什么/优点与对比）、完整可运行代码、依赖包文件（根据项目特征选择格式）、进度摘要。

核心规则：**每轮都输出完整可运行的代码。** Round 1 是骨架（完整头 + 占位符 body）。后续轮次填充 body。用户始终能看到能跑的东西。

## 何时使用

- 用户描述业务需求，期望迭代式地构建代码
- 需求模糊或演进中——用户想通过对话逐步明确
- 用户想要结对编程风格："先搭个骨架" / "一步步来" / "先写个第一版"
- 用户说"先搭结构，再慢慢填"

## 何时不用

- 给已有代码补结构化头 → 用 `$code-formatter`
- 对已有代码做事后数据流 / 影响分析 → 用 `$flow-tracer`
- 用户想要完整的"分析→设计→编码"流水线且每阶段确认

## 函数头标准

每个函数必须带结构化头/文档字符串。使用语言原生风格：

### Python

```python
def function_name(...):
    """
    ROLE:
      <一句话业务职责>

    DEPENDS_ON:
      [upstream_function_a, upstream_function_b]

    IN:
      <输入类型和业务含义>

    OUT:
      <输出类型和业务含义>

    OWNS_FIELDS:
      [field_a, field_b]

    SIDE:
      <INSERT/UPDATE/DELETE/外部调用/文件写入等；无副作用写 None>

    ERRORS:
      <异常、降级或 None 返回语义；无则 None>

    LOG:
      IN/OUT 使用 INFO；关键业务 MAP 使用 INFO；批量细节 DEBUG；可恢复异常 WARNING；中断性异常 ERROR。
    """
```

### JavaScript / TypeScript / Java / C / C++

使用相同的 8 字段结构，采用语言原生格式（JSDoc `/** */`、Javadoc `/** */` 或块注释 `/* */`），按语言习惯放置。

## 思考纪律

每次对话都有一个主旨——这轮工作要达成的目标。所有决策都要对齐它。

### 主旨驱动

主旨不是一开始就明确的，而是通过多轮对话慢慢总结出来的。早期轮次主旨可能模糊，随着对话推进逐渐清晰。

当主旨逐渐清晰时，用一句话记录下来：

> 这次的目标是：<一句话说清要解决什么问题>

主旨明确后，后续的函数分解、填充顺序选择、方向变更都要对齐它。如果用户反馈似乎偏离了主旨，先检查：
- 主旨变了？→ 显式更新主旨。
- 还是只是绕一下？→ 记下来，保持主旨不变。

### 前提条件驱动

搭骨架之前，必须先确认前提条件。没有拿到数据样例和特征之前，不要猜测存储方案和处理逻辑。

| 前提条件 | 为什么要知道 | 没拿到怎么办 |
|---|---|---|
| 数据样例（字段名、类型、几行数据） | 决定字段归属、清洗逻辑、校验规则 | **必须问**——让用户贴几行样例或描述字段 |
| 数据位置（数据库表？文件路径？API？） | 决定 read 函数的签名和依赖 | **必须问**——猜错导致整个骨架废掉 |
| 数据规模（百行？百万行？流式？） | 决定是否需要分批处理、内存策略 | 推断为中等规模，标注假设 |
| 特殊要求（性能？安全？合规？输出格式？） | 决定架构约束 | 推断为无特殊要求，标注假设 |

数据样例是核心——没有数据样例就不写存储和清洗方案，因为字段类型、缺失模式、异常值分布都依赖实际数据。

### 每个方案做方案评审

当你提出任何东西——骨架分解、填充方式、方向变更——都要按三个维度展开方案（框架来自 `$solution-review`）：

**① 方案是什么**——用开发人员能看懂的语言说清方案本身：一句话概述、核心思路（一句大白话能讲明白）、结构、流程、代码骨架（如适用）。

**② 为什么给出这个方案**——要解决的痛点、关键约束（要具体，不说"性能好"要说"QPS 200→1000"）、触发原因、不这么做的后果。

**③ 优点与备选方案对比**——必须列出至少 1 个备选方案，用统一维度（性能/复杂度/可维护性/扩展性/开发成本/风险）对比，论证当前方案为什么胜出，并诚实说明什么情况下应该选别的方案。确实只有一种合理方案时，说明"为什么没有其他选择"，不要硬凑备选。

同时回答批判三问：

| 问题 | 要想什么 |
|---|---|
| **为什么这样？** | 动机是什么？为什么选这个方案而不是另一个？ |
| **有什么缺点？** | 这个方案假设了什么？哪里会失效？ |
| **有没有冲突？** | 和已有的函数、头、之前的决策有没有矛盾？ |

用户应该不只看到你提了*什么*，还要看到*为什么*、*哪里弱*，以及*为什么比别的方案好*。

### 示例

```
骨架方案：read_file → clean_data → validate_rows → transform → write_output → main

① 方案是什么：
  一句话：经典 ETL 线性管道，数据单向流经 5 个处理阶段
  核心思路：每步只做一件事，上一步的输出是下一步的输入，数据不回头。
  流程：读文件 → 去重去空 → 校验必填 → 字段映射 → 写出结果，main 串联。

② 为什么这样分：
  数据流驱动，每步处理一个阶段，read→clean→validate→transform→write 是经典 ETL 骨架。
  关键约束：万级数据内存可处理，无需分批；本周交付，不做过度设计。

③ 优点与对比：
  备选：A. 线性管道（当前） B. 单一大函数一把梭 C. 按业务域拆模块（读取层/处理层/输出层）

  | 维度 | A 线性管道 | B 单一大函数 | C 按域拆模块 |
  |---|---|---|---|
  | 复杂度 | 低 | 最低（但不可维护） | 中 |
  | 可维护性 | 高（每步可单测） | 低 | 高 |
  | 扩展性 | 中（加步骤即加函数） | 低 | 高 |
  | 开发成本 | 低 | 最低 | 中 |

  胜出原因：当前规模下 A 用最低成本拿到可维护性和可单测性；C 的分层在
  只有 5 个函数时是过度设计。
  什么情况下选别的：函数超过 15 个或出现多个独立业务域 → 选 C。

批判三问：
  有什么缺点：
    - 假设单一文件输入；如果需要多文件合并，read_file 要拆成 read+merge 两步
    - validate 和 clean 的顺序可调——先校验再清洗可能更合理（取决于数据脏的程度）
  有没有冲突：
    无。各函数 OWNS_FIELDS 不重叠，DEPENDS_ON 形成线性 DAG，无循环。
```

## 工作流程

### Round 1：搭骨架

#### 步骤 1：收集前提条件 + 定义主旨

先确认前提条件，再搭骨架。前提条件分两层：

**第一层：必须拿到（拿不到就问）**

| 前提条件 | 为什么要 | 示例 |
|---|---|---|
| 数据样例 | 没有数据样例就不写存储和清洗方案——字段类型、缺失模式、异常值都依赖实际数据 | "表有 id(int), name(str), amount(float), date(datetime) 四列，大概长这样：1,张三,100.5,2024-01-01" |
| 数据位置 | 决定 read 函数签名和依赖库 | "MySQL，表名 transactions，连接串 mysql://user:pass@host:3306/db" |
| 核心目的 | 方向错浪费一整轮 | "做月度交易汇总报表" |
| 目标输出 | 没有它定义不了 OUT | "HTML 报表，含汇总表格和趋势图" |
| 包管理工具 | 决定依赖文件格式（requirements.txt / pyproject.toml+lock / Pipfile） | "用 uv" / "用 pip" / "用 poetry" |

**第二层：可以推断（标注假设，用户可纠正）**

| 前提条件 | 默认推断 |
|---|---|
| 数据规模 | 中等规模（万级），内存可处理 |
| 特殊要求 | 无特殊性能/安全/合规要求 |
| 函数分解策略 | 数据流驱动分解 |
| 错误处理 | 合理默认值，写在 ERRORS 里 |
| 日志级别和格式 | 遵循标准 |
| 变量命名 / 类型标注 | 用户可之后改 |
| async / sync | 选更简单的 |

提问时，把所有问题合并成一轮问完。把接近确定的假设表达为假设：

> 我需要知道：
> 1. 数据样例——能贴几行吗？或描述一下字段名和类型
> 2. 数据在哪——MySQL？PostgreSQL？文件？
> 3. 输出格式——HTML？Excel？PDF？
> 4. 包管理工具——pip？uv？poetry？pipenv？
>
> 我假设数据规模是万级、无特殊性能要求。如果不对请告诉我。

拿到前提条件后，不要在写骨架之前请求确认骨架设计。写出来，让用户看。

**然后尝试用一句话总结主旨（可能还不清晰，没关系）：**

> 这次的目标是：<一句话说清要解决什么问题>

主旨可能在早期轮次还比较模糊，随着对话推进会逐渐清晰。当前能总结多少就写多少，后续轮次再修正。

#### 步骤 2：识别核心函数

根据数据流，每个独立的业务操作对应一个函数：

- 输入 / 解析
- 校验
- 核心转换（可能多个）
- 输出 / 持久化
- 入口 / 编排

保持最小化——不要过度分解。骨架展示的是核心结构，不是每个辅助函数。目标 3-7 个核心函数。

#### 步骤 3：写骨架

对每个核心函数：

1. **写完整的 8 字段头**——这是设计契约。虽然 body 是占位符，但头必须完整，准确描述*预期*行为。

2. **写占位符 body**，用以下两种模式之一：

**模式 A — Raise（关键路径，调用占位符应该响亮地失败）：**

```python
def clean_data(raw_df: pd.DataFrame) -> pd.DataFrame:
    """
    ROLE:
      对原始数据去重去空并标准化字段名

    DEPENDS_ON:
      [read_file]

    IN:
      raw_df: pd.DataFrame — 原始未清洗数据

    OUT:
      pd.DataFrame — 清洗后的数据

    OWNS_FIELDS:
      [cleaned_df]

    SIDE:
      None

    ERRORS:
      None

    LOG:
      IN INFO (row count); OUT INFO (cleaned row count, removed count)
    """
    # TODO(round-1): 实现去重去空逻辑
    raise NotImplementedError("去重去空逻辑待实现")
```

**模式 B — Stub 返回（骨架需要端到端跑通以验证结构）：**

```python
    # TODO(round-1): 实现去重去空逻辑
    return raw_df.copy()  # stub: 暂不处理，原样返回
```

根据用户是否需要端到端运行骨架来选择：

| 模式 | 何时使用 |
|---|---|
| `raise NotImplementedError` | 关键路径；stub 会掩盖结构问题 |
| `return <stub>` | 用户想跑通骨架验证管道形状 |

3. **包含入口函数**——一个 `main()` 或等价函数，按数据流顺序调用各函数。

#### 步骤 4：输出骨架 + 前提条件 + 依赖包 + 方案评审 + 进度摘要

输出五样东西：

1. **前提条件记录**——把收集到的前提条件列出来，让用户确认没理解错：

```
前提条件：
  数据样例：id(int), name(str), amount(float), date(datetime)
  数据位置：MySQL，表 transactions
  数据规模：万级（推断）
  特殊要求：无（推断）
  输出格式：HTML 报表
  包管理工具：uv
```

2. **完整的骨架代码**——所有函数含头 + 占位符。必须语法有效、可导入。

3. **依赖包文件**——先确认用户用什么包管理工具，再选格式：

| 环境/工具 | 输出文件 | 安装命令 | 说明 |
|---|---|---|---|
| 传统 pip | requirements.txt | `pip install -r requirements.txt` | pip 标准格式，每行一个包 |
| uv | pyproject.toml + uv.lock | `uv sync` | uv 原生方式，锁文件保证可复现 |
| poetry | pyproject.toml + poetry.lock | `poetry install` | poetry 原生方式 |
| pipenv | Pipfile + Pipfile.lock | `pipenv install` | pipenv 原生方式 |
| 补充说明（可选） | requirements.yaml | — | 结构化，记录每个包用途/版本约束理由，给人看 |

**判断规则**：Round 1 收集前提条件时，问用户用什么包管理工具。根据回答选择对应格式：
- 用户说 pip 或没说 → requirements.txt
- 用户说 uv → pyproject.toml + uv.lock（用 `uv add <包名>` 添加依赖）
- 用户说 poetry → pyproject.toml + poetry.lock（用 `poetry add <包名>` 添加依赖）
- 用户说 pipenv → Pipfile + Pipfile.lock
- 用户想额外记录用途 → 追加 requirements.yaml 作为补充

**requirements.txt 示例**（pip）：
```
# req-to-code 依赖包
sqlalchemy>=2.0  # 数据库连接和查询
pandas>=2.0      # 数据处理
jinja2            # HTML 报表渲染
```

**pyproject.toml 示例**（uv / poetry 通用）：
```toml
[project]
name = "<项目名>"
version = "0.1.0"
dependencies = [
    "sqlalchemy>=2.0",  # 数据库连接和查询
    "pandas>=2.0",      # 数据处理
    "jinja2",            # HTML 报表渲染
]

[project.optional-dependencies]
dev = [
    "pytest",
    "ruff",
]
```

**requirements.yaml 示例**（补充说明，给人看）：
```yaml
project: <项目名>
package_manager: uv  # 或 pip / poetry / pipenv
dependencies:
  - name: sqlalchemy
    version: ">=2.0"
    purpose: 数据库连接和查询
  - name: pandas
    version: ">=2.0"
    purpose: 数据处理
  - name: jinja2
    purpose: HTML 报表渲染
```

4. **骨架方案的评审（三维度 + 批判三问）：**

```
骨架方案：<函数列表和数据流>

① 方案是什么：
  一句话：<概述>
  核心思路：<一句大白话讲明白>
  流程：<数据怎么流>

② 为什么这样分：
  <动机：为什么这样分解；关键约束要具体>

③ 优点与对比：
  备选：<至少 1 个备选分解方案>
  | 维度 | 当前方案 | 备选 |
  |---|---|---|
  胜出原因：<论证>
  什么情况下选别的：<适用边界>

批判三问：
  有什么缺点：<局限：这个方案假设了什么，哪里会失效>
  有没有冲突：<一致性：和已有决策有没有矛盾>
```

5. **进度摘要：**

```
ROUND 1 — 骨架
══════════════════
主旨：<一句话主旨>
前提条件：数据样例 ✓ | 数据位置 ✓ | 包管理工具 ✓ | 规模（推断） | 特殊要求（推断）

函数数：6
  ✅ 头完整：    6
  🔲 body 填充： 0
  📝 TODO：     6

依赖包文件：<根据项目特征选定的格式，见步骤 4 判断规则>

TODO 清单：
  1. read_file       — 读取 CSV 文件为 DataFrame
  2. clean_data      — 去重去空并标准化字段名
  3. validate_rows   — 校验必填字段
  4. transform       — 字段映射和格式转换
  5. write_output    — 写入结果文件
  6. main            — 串联管道入口

下一步：告诉我先实现哪个，或直接说"继续"我按数据流顺序填充。
```

Round 1 不要跑 7 规则一致性检查——占位符 body 没有真实逻辑可查。

---

### Round 2+：增量填充

#### 步骤 1：读取当前状态

扫描已有代码：函数头、`# TODO(round-N)` 标记、`DEPENDS_ON` DAG。

#### 步骤 2：决定填充什么

根据用户输入：

| 用户说 | 动作 |
|---|---|
| "实现 clean_data" / 指定函数名 | 填充该函数 |
| "继续" / "next" / "继续填" | 按数据流顺序填充（upstream first） |
| 新需求 / 方向变更 | 见下方"处理方向变更" |
| 对已填充代码的反馈 | 修改指定函数 |

**默认填充顺序**：upstream first——先填 `DEPENDS_ON` 已经填好的函数。

如果存在多种实现方式，在编码前按方案评审三维度简要展开：是什么、为什么选它、和备选方式的对比（统一维度）+ 缺点。只有一种合理方式 → 直接写，但说明"为什么没有其他选择"。

#### 步骤 3：填充函数 body

对本轮要填充的每个函数：

1. **移除占位符**——删除 `# TODO(round-N)` 标记和 `raise` / stub。

2. **实现 body**——目标 ≤30 行。使用管道式变量名揭示转换链：

```python
raw_headers -> cleaned_headers -> header_map
```

不要对不同的语义状态复用同一个变量名。

3. **添加结构化日志**，匹配 `LOG` 头字段：

| 阶段 | 级别 | 何时使用 |
|---|---|---|
| IN | INFO | 关键输入用于追踪 |
| OUT | INFO | 关键输出或结果摘要 |
| MAP 单条 | INFO | 业务关键字段映射 |
| MAP 批量 | DEBUG | 批量映射、逐行细节 |
| ERR 可恢复 | WARNING | 降级、跳过、重试 |
| ERR 致命 | ERROR | 操作中断 |

日志格式：`业务动作名 | 阶段(IN/MAP/ERR/OUT) | key=value`

不要记录密钥、密码、token、完整 PII 或大体积数据。

4. **行为变化时更新头：**

| 填充时发现... | 更新的头字段 |
|---|---|
| 新建/修改了字段 | `OWNS_FIELDS` |
| 新的副作用 | `SIDE` |
| 新的异常或降级 | `ERRORS` |
| `LOG` 里没有的新日志点 | `LOG` |
| 输入用法变了 | `IN` |
| 返回形状变了 | `OUT` |
| 调用了新的上游依赖 | `DEPENDS_ON` |

#### 步骤 4：跑一致性检查（仅变更函数）

对本轮变更的每个函数跑 7 规则检查：

| # | 规则 | STALE（头多声明了） | MISSING（头少声明了） |
|---|---|---|---|
| 1 | `OWNS_FIELDS_MATCH` | 声明的字段 body 没操作 | body 操作了未声明的字段 |
| 2 | `DEPENDS_ON_MATCH` | 声明的依赖没调用 | body 调用了未声明的函数 |
| 3 | `SIDE_MATCH` | 声明的副作用没执行 | body 有写操作但 `SIDE: None` |
| 4 | `IN_MATCH` | 描述的参数不在签名里 | 签名参数没描述 |
| 5 | `OUT_MATCH` | 声明的返回形状从没返回 | 返回了未声明的形状 |
| 6 | `LOG_MATCH` | 描述的日志没有对应语句 | 有日志但 `LOG` 没描述 |
| 7 | `ERRORS_MATCH` | 描述的异常没有对应代码 | body 抛出/处理了未声明的异常 |

输出前修复所有 STALE 和 MISSING。

#### 步骤 5：输出更新后的代码 + 进度

输出：

1. **完整的更新后代码**——每轮都是完整可运行状态。

2. **进度摘要：**

  （本轮无新增；如引入新依赖，同步更新依赖包文件并标注 +包名）

### 处理方向变更

用户中途改需求（新功能、不同方案、范围变化）时：

1. **重新读取当前状态**——什么已建，什么还是占位符。
2. **评估影响**——哪些函数受影响。
3. **做方案评审**：
   - 是什么：变更后的新方案是什么样（一句话 + 核心思路）
   - 为什么改：变更的动机、关键约束
   - 对比：新方案 vs 原方案（统一维度），为什么新方案胜出
   - 有什么缺点：变更破坏了什么或假设了什么
   - 有没有冲突：和已填充函数的矛盾

4. **直接应用变更**（除非有歧义才问）：

   | 影响 | 动作 |
   |---|---|
   | 已填充函数行为要变 | 更新头，body 替换为 `# TODO(round-N): rework — <原因>` + 占位符 |
   | 函数不再需要 | 删除；更新引用它的函数的 `DEPENDS_ON` |
   | 需要新函数 | 添加完整头 + 占位符 body；更新下游 `DEPENDS_ON` |
   | 输入/输出格式变了 | 传播到受影响函数的 `IN`/`OUT`/`OWNS_FIELDS` |

5. **更新 DEPENDS_ON DAG。**

## 规则

- **每轮输出完整可运行代码**——不要片段或局部文件。
- **搭骨架前先收集前提条件**——数据样例、数据位置、核心目的、目标输出是必须拿到的；没有数据样例不写存储和清洗方案。
- **每轮输出依赖包文件**——Round 1 确认包管理工具（pip/uv/poetry/pipenv），选对应格式（requirements.txt / pyproject.toml+lock / Pipfile）；引入新依赖时同步更新。
- **每次对话有主旨**——Round 1 尝试总结（可能模糊），随对话推进逐渐清晰，每轮检查对齐。
- **每个方案做方案评审**——三维度展开：是什么（说清方案本身）、为什么（动机+具体约束）、优点与对比（至少 1 个备选、统一维度、诚实说明适用边界）；并回答批判三问：为什么这样、有什么缺点、有没有冲突。框架来自 `$solution-review`。
- **函数头是持久真实来源**——Round 1 就完整，行为变化时更新。
- **占位符 body** 使用 `# TODO(round-N): <描述>` + `raise NotImplementedError` 或 stub 返回。
- **尽量少提问**——能推断就推断，写完让用户看。
- **只在严重缺失信息会导致骨架结构性错误时才问。**
- **用户说"继续"时 upstream first** 填充。
- **填充改变行为时更新头。**
- **每轮对变更函数跑 7 规则一致性检查**；最终轮全量检查。
- **方向变更**：直接应用，标记 rework 函数，更新 DAG，做方案评审（含新旧方案对比）。有歧义才问。
- **头里全用业务语言**——不要实现术语。
- **日志不暴露密钥**——记数量、ID、摘要。
- **每个可变/派生字段有且只有一个归属函数。**
